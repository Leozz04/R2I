# 规则设立指南（新项目，从零开始）

> 给引导会话（BOOTSTRAP 第 6 步）和项目负责人看。假设这是一个全新项目：不沿用任何旧项目的规则内容。r2i 只带来**机制**（台账、要批页、交接检查、花费闸门），规则内容由负责人在这里定。

规则分两层，版本号各自计数：

| 层 | 文件 | 内容 | 谁改 |
|---|---|---|---|
| 核心 | 项目的 `rules/core.md`（从 `tools/r2i/rules/core.md` 复制） | 编号 R-xx，程序依赖的机制规则（问负责人走 `r2i ask`、花钱走 `r2i paid-run`、事实正本是台账……） | 可以改，但改了要知道哪个程序在依赖它；改动记版本 |
| 项目 | 项目的 `rules/project.md`（从 `project.md.example` 复制） | 部门表、分工、路径、只对本项目成立的规矩，编号 P-xx 和各组字母 | 照 R-50a 的流程 |

两层拼成 vault 根目录的 `项目规则.md`，线程只读这一份；`agent/必带清单.md` 是开工要带的摘要，入口文件由它生成。

---

## 1. 负责人决策权清单（附录一）

这是整套规则里最要紧的一张单子：**只有单子上的事线程才问负责人，其余线程自己定**，写一行「已按 X 做 · 不同意勾「改」」接着做。单子太长，线程什么都问，负责人被淹；太短，重要的事被线程自己定了。

先过一遍下面的类别，每类让负责人选「我管 / 线程定 / 不适用」，管的写一句「什么时候算」。**这里只是结构和例子，不是推荐答案**，按项目实际改。

| 类别 | 例子（帮助理解，不是默认值） | 我管 / 线程定 / 不适用 | 什么时候算 |
|---|---|---|---|
| 方向 | 新想法、新研究方向要不要开 | | |
| 目标 | 改主线目标、改验收线 | | |
| 叫停 | 停掉或换掉一条实验线 | | |
| 开跑 | 线程复述完想法后，由负责人说「开跑」 | | |
| 花费 | 单笔超过 `approve_over` 的花费；夜间预算；充值 | | |
| 权限 | 改 agent 能读写的路径、能跑的命令 | | |
| 删除 | 删数据、删分支、删页面 | | |
| 对外 | 发邮件、发布、push、合并、上传数据集、公开任何东西 | | |
| 本人操作 | 登录、钥匙串、装系统任务、重启机器 | | |
| 结论 | 论文结论和对外数字定稿前 | | |
| 规则 | 改项目规则、改审计规则 | | |
| 抽查 | 抽查线程或审计自己定了的事 | | |

另外问一句「**明确不用问我的**」，例如：改代码、小实验开和结、两个选项明显一个更好时选哪个、预算内租算力。写进附录一末尾「负责人不管的」那一行。

写法：项目 `rules/core.md` 的「附录一」照这个格式编号列出，一条一行：

```
1. 对外：发邮件、push、上传数据集、公开任何内容。只认我在执行线程里亲手打的字。
2. 花费：单笔 {{currency}} {{approve_over}} 以上。
…
负责人不管的：改代码；小实验的开和结；预算内租算力。
```

有三条硬线不管单子怎么写都在：**删除、对外、改账或账号**只认负责人亲手打的字（R-10a），花钱走 paid_run（R-21），不对外公开（R-71）。这三条有程序或权限拦着；要放宽，先改权限设置，再改规则。

## 2. 必带清单怎么写

`vault/agent/必带清单.md` 是每条线程开工唯一必读的一页。原则：

- **一页、编号、每条一两句**，末尾括号标对应的规则号（例如「（R-10）」），细节在规则里，这里不展开。
- 只放「每条线程每天都会碰到」的事：怎么问负责人、怎么花钱、事实正本在哪、数据放哪、交接怎么写、什么不能做。只对某个部门成立的放规则「分工」那一节。
- 写成命令而不是原则：「问负责人的同一轮跑 `r2i ask`」比「及时沟通」有用。
- 改了必带清单就跑 `r2i entries --vault vault`，项目根目录和 vault 的 `CLAUDE.md`/`AGENTS.md`/`GEMINI.md` 由它生成，不手改那些文件。
- 规则更新只写进必带清单和规则页，不逐条去提醒线程重读：线程下次开工自然会读到。

模板里已经有一份按 `core.md` 写好的清单，新项目要做的是：把附录一的类别填进第 4 条的说法里，把部门表、模型分档（第 17 条）改成本项目的实际情况，删掉用不上的条目。

## 3. 交接、验收线、预注册：最小规矩

**交接**（R-43）：每条主线一页 `agent/交接/<短名> 交接.md`，是「现状」不是日志，每次整段重写，≤1.5 万 token。最少四节：目标卡（目标 + 验收线，由程序从台账生成）、在跑什么、做过的决定、下一步。结案前跑 `r2i handover-check --mainline <id>`，有 FAIL 不能结。上下文到 30 万 token 左右（或第一次自动压缩）写交接、请调度者开接班。

**验收线**：每条主线的目标用 `r2i goal-set` 写进台账，带 2–5 条可检查的验收线（「在 X 数据上 Y 指标 ≥ Z」，不写「效果好」）。目标和验收线的改动归负责人（附录一「目标」类）。每个实验行带 `crit=<验收线 id>`，说明它推哪条线；哪条都不推写 `crit=无:理由`。

**预注册**：开跑一个要花钱或要几小时以上的实验前，在实验行或任务记录里写下三件事再跑：要回答的问题、过线标准（数字）、结果出来后各自意味着什么决定。跑完照实对照，不事后改线。改线要单独写原因，结论标「事后」。

## 4. 静默时段和夜间

- `quiet_hours`（默认 `00:00-09:00`，按 `tz`）内不推送通知、不在线程里等负责人回。碰到附录一里的事照样当轮 `r2i ask` 开页，程序把通知压到静默时段结束后发。
- 夜里不归负责人管的事线程自己定、接着做；只有一条线每条路都卡在附录一的事上才停，停之前把不用负责人定的都做完（R-53）。
- 夜间要花钱的工作走夜间预算 `night_budget`：负责人设一次长期有效，夜间队列由负责人在页上勾选。
- 静默时段不开新线程、不开接班；到线的线程交接照写，靠自动压缩接着跑，静默时段结束后再交接。

要问负责人的：负责人的作息、能不能接受夜里跑实验、夜间预算多少。

## 5. 花费分级（approve_over）

| 档 | 条件 | 谁定 | 怎么走 |
|---|---|---|---|
| 小额 | 单笔 ≤ `approve_over` | 线程自己 | `r2i budget-add` 登记 → `r2i paid-run --budget <id> --cap <数> -- <命令>` |
| 大额 | 单笔 > `approve_over` | 负责人 | `r2i ask` 开要批页，按七段写：名称、要回答的问题、怎么做（≤3 步）、花多少多久、成功意味着什么、失败意味着什么、不做什么 |
| 夜间 | 静默时段内 | 负责人设的夜间预算 | 夜间队列 |

花之前先 `r2i res-list` 看资源台，每个要用的钥匙先做一次最小调用（R-20）。所有调用都失败的按 0 结算。`approve_over` 定多少看项目的钱和节奏，常见是一顿饭钱量级；改它就是改 `r2i.toml`，同时在规则版本记录里记一行。

## 6. 写进 vault 正本

1. 项目根目录建 `rules/`：`core.md`（复制后填好附录一）、`project.md`（从 example 复制后填好）。
2. 拼 `vault/项目规则.md`：保留模板的 frontmatter 和开头一段；「第一部分」整段换成 `rules/core.md` 的内容，「第二部分」换成 `rules/project.md`；`{{owner}}` 等占位符换成 `r2i.toml` 里的值。frontmatter 的 `version` 写成 `core v1.0 + project v1.0`。
3. 改 `vault/agent/必带清单.md`（第 2 节），然后 `r2i entries --vault vault`。
4. 把附录一、主线目标和验收线给负责人过目；负责人在对话里认可后，`r2i goal-set … --approved-by '<负责人>'` 写台账。
5. 以后改规则走 R-50a：线程写提案、压到三行，负责人打字批；每改一次升 0.1，同时改 `rules/*.md`、`项目规则.md` 和版本记录表。一条规则只有一个正本，别处只放链接（R-32）。

加新规则之前先过三问（R-50）：有没有出过事的证据；能不能写成程序；能不能加在现有的东西上。
