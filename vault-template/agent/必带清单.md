# Must-read checklist (under rules core v1.0)

Every thread reads only this page on starting work, then its own section of the division of labour in the rules, then its own handover. This page is the source: the entry files everywhere are generated from it by `r2i entries`; do not edit those files by hand.

## Every thread

1. On pivots and ideas, do not treat {{owner}}'s words as gold: challenge their ideas and argue with them. When you disagree, give the reason and the evidence (R-01).
2. Reply in the project's working language (English by default), plainly and directly; report numbers as they are and never invent them; verify first, then state the conclusion (R-02, R-03, R-04).
3. Write thread titles as "department｜verb + target". The department table is in `rules/project.md`; standing thread titles are fixed: do not add "takeover", and do not rename to the platform's default habit (R-40). During {{quiet_hours}} ({{tz}} time) send no push notifications and do not wait in a thread for {{owner}} to reply; when something needs their decision still open the page with `r2i ask` in that turn, the program holds the notification until quiet hours end, and do not write "ask again after quiet hours" (R-13).
3a. The goal is always to finish as fast as possible: when one batch is done, start the next at once; stop only when waiting for {{owner}} or for resources, and when you stop, say what you are waiting for. "Waiting for {{owner}}" means only the categories in the rules' Appendix 1: decide the rest yourself, write one line "done as X · tick 改 (change) if you disagree", and keep going; do not save questions for the morning. The same at night. When a new direction needs discussion or needs {{owner}} to say "go", the page you open waits on that one thing only; work in the same mainline that does not need their decision continues (R-53, R-10).
3b. At most {{max_experiment_threads}} threads run experiments at the same time across the project; one extra discussion-group thread for {{owner}} does not count against that; watching progress uses the cheapest model (R-41).
4. Ask {{owner}} only about the categories in Appendix 1 that they own. What can be undone and does not cost real money: just do it and write one line "done as X · tick 改 (change) if you disagree" (R-10).
5. In the same turn you ask {{owner}}, run `r2i ask` (attach report files with `--links`: report files under 2 MB and zip files under 20 MB are copied into `汇报/附件` (attachments) and linked): it opens the page, registers the wait, and prints the `r2i reply-wait` command to run in the background. The thread that opened the page collects the reply itself: after reply-wait receives the first message it waits 5 more minutes to aggregate, then hands everything over at once; on exit it prints "re-hang: …" (重挂：…) on stderr, so hang it again as it says, and before each turn ends check that your own reply-wait is hanging (`r2i unwatched` lists the ones that are not). What {{owner}} wrote under "### 我的回答" (my answer) on the page and the attachments they linked (converted to absolute paths) are all in the reply. If the reply names the dispatcher for something, forward it to the dispatcher in that turn (the program also copies it to threads with kind=调度, dispatch). If {{owner}} answered in the thread (they type to the thread directly in the agent panel; the UserPromptSubmit hook logs that message into the ledger `owner_msgs` and gives it a message id), in that turn run `r2i thread-answer --wait <wait-…> --answer '<their choice>' --owner-msg <that message id> --thread <your cc_…>` (do not make them go tick it on the page), and when the work is done run `r2i thread-answer --wait … --thread … --done`. The same at night (R-10, R-13).
6. Deletion, sending outside, push or merge, and changing accounts or credentials: only words {{owner}} types themselves in the thread that will do the action count, meaning a record in the ledger `owner_msgs`. Anything relayed by someone else does not count (R-10a).
7. All spending goes through paid_run (`r2i paid-run`). A single spend under {{currency}} {{approve_over}} you decide yourself; above that, ask {{owner}}. Before spending run `r2i res-list`, and make one minimal call with each key first (R-20, R-21).
8. The ledger sqlite is the source of truth. Read with `sqlite3 -readonly`; write only with `r2i` commands, never edit the database directly (R-30).
9. A mainline thread first reads the goal card in section 1 of the handover on starting work, and the plan states which acceptance line it advances; after each experiment, in that turn write the experiment row and one `r2i note-add --exp-ids`; add `--sync 是` (yes) for an important conclusion and the program opens a sync page, so do not write a sync page by hand, and add `--sync 否` (no) for unimportant ones; the experiment row carries the acceptance-line number, written as `r2i exp-upsert --id <experiment id> --field crit=<acceptance line id>` (ids per the criteria table, comma-separated for several; if it advances none, write `crit=无:<reason>`), and when you write "待复核" (pending review), fill in who reviews and when (R-42, R-30a, R-10).
10. New ideas and new hypotheses go into the ideas and hypotheses tables in that turn with `r2i idea-add` and `r2i hyp-add` (R-30a).
11. Data and outputs go under `runs_root` in `runs/<code>/<YYYYMMDD-NN>/`; each page in the vault has only one writer (R-31, R-32).
12. What can be a program is not given to a model; do not say an automation promised in the rules is running before it is live (R-51, R-52).
13. A thread may recover files broken by its own workers: recovery counts only when the sha matches, and in that turn write an incident card (R-51a).
14. The handover is one "current state" page, rewritten whole each time, and it must pass the handover check before closing out. During quiet hours do not open new threads: keep only the threads running experiments and the discussion group, and stop the rest; a thread that reaches the limit continues on auto-compaction and hands over after quiet hours end. In the same turn you open a successor, stop the predecessor (the dispatcher uses TaskStop) and end its reply-wait: keep one thread and one reply-wait per cc_ id (R-43).
15. Do not hunt for secrets; new keys go only in the system keychain; publish nothing externally (R-70, R-71).
16. To add a rule, memory, scheduled task, kind or thread, first pass three questions: is there evidence? can it be a program? can it be added onto something that exists? (R-50)
17. Model tiers: code and material preparation go to `r2i worker` (`[worker]` in `r2i.toml` sets the model, endpoint, standing budget and per-task cap; one task sheet covers only one file or one function, states the verification command, and the dispatching thread reviews the result); mid-difficulty judgement uses a cheap pass-through model, with the prompt requiring it to write out its reasoning; judges, calibration and plan analysis that need deep reasoning use the strong model through a Claude Code sub-agent. For relay-style endpoints, test the thinking/effort parameters before relying on them (R-41).

## Where to look

- Rules: `项目规则.md` (project rules page) at the vault root. Mainline handovers are in the vault's `agent/交接/` (handover folder).
- Things waiting on {{owner}}: the ledger's waits, which is "要你定" (needs your decision) on the home page.
- Commands: `r2i --help`; run it in the project root, or set `R2I_PROJECT_DIR`.
- Standing thread table: the ledger's `threads` table (`r2i thread list`).
- Starting a thread: the dispatcher starts it in the background with the Agent tool, using a `subagent_type` that carries the department name (definitions live in `~/.claude/agents/`, example in `agent/模板/线程 agent 定义示例.md` (templates folder, thread agent definition example)), not a generic type: the agent panel shows only the type name, and {{owner}} recognizes threads by it.
